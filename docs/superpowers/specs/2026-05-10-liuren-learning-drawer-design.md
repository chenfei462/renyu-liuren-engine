# `/app` 学习闯关抽屉设计说明

日期：2026-05-10

## 目标

把 `/app` 里的“学习闯关”从不可点击的静态条目列表，改成一个真正可用的学习入口。

这次改造只解决三件事：

1. 用户一眼能看出“下一步学什么”。
2. 每个学习节点都能点开，并且点开后有明确内容，而不是只显示英文标题和状态字样。
3. 不打断 `/app` 的主流程。起课和解读仍是主路径，学习闯关是右侧可进入的辅路径。

不在这次范围内：

- 新建独立学习页面路由。
- 引入复杂题目系统、测验系统或账号体系。
- 重做学习数据结构。

## 外部参考

这次交互方向参考了 3 类当前仍在更新的学习产品说明：

- Brilliant 的 Learning Paths 强调“按顺序学习、互动练习、阶段检查点”。其公开帮助页最后更新于 2025-10-29。[Brilliant](https://brilliant.org/help/using-brilliant/what-are-learning-paths/)
- Codecademy 的 Paths 强调“明确路径类型、里程碑、课程/测验/项目顺序”。其帮助页更新时间为 2026-01-30。[Codecademy](https://help.codecademy.com/hc/en-us/articles/220453248-Picking-Your-Learning-Path)
- Khan Academy 的 Mastery 体系强调“进度可见、技能状态、课程挑战与推荐下一步”。其相关帮助页更新时间为 2024-09-19。[Khan Academy](https://support.khanacademy.org/hc/en-us/articles/115002552631-What-are-Course-and-Unit-Mastery-)

可借鉴的共性，不照抄形式：

- 学习路径必须给出推荐下一步，而不是纯列表。
- 节点必须可点击，并能展开为更具体的信息层。
- 进度或状态必须清楚，但不能伪造“已完成率”。
- 不可用内容必须明确标注，不要让用户点击后才发现不能用。

## 当前问题

当前实现里，`learningPathList` 只把 `/api/learning/path` 的前 6 个节点渲染成：

- 标题
- `review_status`

没有：

- 可点击目标
- 当前推荐项
- 节点详情
- 状态翻译
- 关联学习卡内容
- 明确动作按钮

这导致用户看到的是“信息清单”，不是“可操作路径”。

## 设计方向

采用“右侧独立学习抽屉”方案。

具体选择：

1. 把 `#learningPathPanel` 从 `#experimentsPanel` 中移出。
2. 将其放入右侧 `aside#supportPanel`。
3. 位置放在 `#learningMaterials` 后、`#feedbackPanel` 前。
4. 容器使用独立的 `details.panel.rail-card`，与“学习资料”并列，而不是并入其内部。

这样做的原因：

- 不破坏左侧“输入问题 -> 起课 -> 看结果”的主工作台。
- 学习路径不再被归类为“实验功能”。
- 现有移动端断点下，`assistant-rail` 已经会自然堆叠到底部，不需要重做主布局。
- 右栏内部形成清晰顺序：访问状态 -> 学习资料 -> 学习闯关 -> 反馈。

## 信息架构

### 抽屉关闭态

关闭时只显示一行摘要，不再是空白列表：

- 标题：`学习闯关`
- 副文案：`从基础结构到安全边界，按节点学习。`
- 简要统计：
  - 总节点数
  - `approved_for_mvp` 数量
  - `research_only` 数量
- 如果有推荐节点，显示 `推荐下一步：四课 / 三传 / …`

关闭态本身可点击展开。

### 抽屉展开态

展开后分成 3 个区域。

#### 1. 推荐学习项

放在最上方，视觉权重最高。

包含：

- 标签：`推荐下一步`
- 节点标题
- 一句话说明这节是干什么的
- 状态标签：`可学` 或 `研究中`
- 元信息：
  - 学习卡数量
  - 出处数量
  - 示例数量
- 主按钮：
  - `开始学习`：`approved_for_mvp`
  - `暂不可学`：`research_only`，禁用

推荐规则：

- 先取第一个 `approved_for_mvp` 节点。
- 如果未来已有本地学习进度，再改成“最近未完成的可学节点”。

#### 2. 全部节点列表

推荐项下面展示完整节点列表，而不是只展示 6 个。

每个节点是一个可点击卡片按钮，不是纯文字段落。

每张卡显示：

- 标题
- 中文状态标签
- 1 行简述
- 次要统计：学习卡、出处、示例
- 当前选中态

状态翻译：

- `approved_for_mvp` -> `可学`
- `research_only` -> `研究中`

#### 3. 节点详情区

点击节点卡片后，在抽屉内部显示详情区。

详情区包含：

- 节点标题
- 状态说明
- 这节能帮用户看懂什么
- 关联学习卡摘要列表
- 关联出处编号列表
- 关联输出类型列表（来自 `unlocked_outputs`）
- 一个动作区

动作区定义：

- `查看学习卡`：把关联学习卡直接在详情区展示出来，不跳页。
- `标记已读`：优先调用现有 `/api/learning/progress`。如果产品化闸门未开放，就显示“当前不保存进度，不影响浏览”。

不新增“考试”“打卡”“闯关积分”之类伪进度系统。

## 内容映射

### 可复用数据

来自 `/api/learning/path`：

- `node_id`
- `title`
- `learning_card_ids`
- `source_ids`
- `example_case_ids`
- `review_status`
- `unlocked_outputs`

来自 `/api/learning/cards`：

- `card_id`
- `title`
- `summary`
- `tags`
- `source_ids`

### 前端组装规则

前端在加载学习抽屉时：

1. 拉取 `/api/learning/path`
2. 拉取 `/api/learning/cards`
3. 用 `learning_card_ids` 把路径节点与学习卡 join 起来
4. 生成每个节点的中文简述

### 节点简述规则

当前数据里没有现成的用户可读短说明，因此前端先按 `topic` 或 `node_id` 做一层轻量映射，生成短说明。

示例：

- `four_lessons` -> `先看四课结构，理解课体骨架。`
- `three_transmissions` -> `理解事情从起因到收束的推进路径。`
- `generals` -> `把天将当作象征角色来读，不当成现实承诺。`
- `safety_boundary` -> `先学哪些问题不能直接下现实结论。`

这层映射先放在前端常量中，不改后端数据文件。

## 交互规则

### 打开方式

用户可通过两种方式打开：

- 点击学习闯关抽屉本身的 `summary`
- 点击顶部导航中的相关学习入口时，自动展开该抽屉并滚动到位

### 节点点击行为

点击节点卡片时：

1. 节点进入选中态
2. 详情区刷新
3. 抽屉保持打开
4. 页面不跳转
5. 键盘 focus 保持可见

### 推荐项按钮行为

点击 `开始学习` 时：

1. 自动选中推荐节点
2. 滚动到详情区顶部
3. 详情区加载对应学习卡
4. 如可用，触发一次 `learning_progress` 记录，状态为 `started`

### 研究中节点

`research_only` 节点仍允许点开详情，但要明确表现为“只读说明”：

- 状态标签使用低饱和样式
- 主按钮禁用
- 文案写清楚：`当前仅供研究参考，暂不作为公开学习节点`

### 失败态

如果学习路径接口失败：

- 抽屉内显示：`学习路径暂不可用`
- 保留一个重试按钮不是必须，本次可以先只显示失败文案

如果学习卡接口失败但路径接口成功：

- 节点列表仍显示
- 详情区显示：`关联学习卡暂不可用`

## 视觉与可用性

### 组件层次

推荐学习项和节点详情的权重高于节点列表。

原因：

- 用户首先需要下一步，不是先扫完整树。
- 详情区必须证明“点开后有内容”，否则还是假交互。

### 样式方向

保持现有纸面工作台风格，不另起一套设计语言。

新增视觉重点：

- 推荐项卡片要明显区别于普通节点
- 节点卡片 hover、active、focus 必须可见
- 状态标签应中文化并可一眼区分
- 详情区与列表之间要有边界，不让信息糊成一片

### 可访问性

必须满足：

- 可点击节点使用 `button` 或具备按钮语义的元素
- 键盘可聚焦
- `focus-visible` 清晰可见
- `details/summary` 的打开逻辑不与键盘行为冲突
- 选中节点可通过 `aria-pressed` 或 `aria-current` 风格状态表达

## 技术实现边界

这次优先做前端增强，后端只复用现有接口。

预期改动文件：

- `static/realtime/index.html`
- `static/realtime/styles.css`
- `static/realtime/app.js`
- `tests/test_realtime_frontend.py`

如需补充契约，可追加：

- `tests/test_phase13_productization.py`

本次不要求新增后端接口。

## 测试策略

先写前端契约测试，再实现。

至少覆盖：

1. 学习闯关面板已从 `experimentsPanel` 提升到右侧辅栏。
2. 学习闯关是独立 `details` 抽屉，不再是静态 `div` 列表。
3. 节点渲染为可点击项，而不是纯 `<section class="mini">`。
4. 点击 `approved_for_mvp` 节点会刷新详情区。
5. 点击 `research_only` 节点会显示只读说明，并禁用主按钮。
6. 推荐学习项存在，并能触发同一套节点选择逻辑。
7. 路径接口成功但学习卡接口失败时，列表仍可见，详情区显示降级文案。
8. 移动端结构不把学习抽屉重新塞回实验区。

## 验收标准

- 用户打开学习闯关后，第一眼能看到一个明确的推荐下一步。
- 每个节点都可以点。
- 点开节点后，有详情、有学习卡摘要、有状态说明。
- `research_only` 节点不会伪装成可学内容。
- 学习闯关不再放在“更多 / 实验功能”里。
- 右侧辅栏信息层级更清楚，且不压过左侧起课主流程。
- 375px、768px、1024px、1440px 宽度下，抽屉内容无明显溢出、重叠或无法点击。

## 风险与折中

- 现有 `learning_path` 数据缺少直接面向用户的短说明，因此首版需要前端维护一层简述映射。
- 现有 `/api/learning/progress` 在产品化闸门未开放时不会真正存储，所以“标记已读”首版只能做到有反馈、不承诺持久化。
- 如果把详情区做得太长，右栏会再次变成信息堆，因此必须保持推荐卡、节点列表、详情区之间的层次克制。

## 结论

首版不追求完整学习系统，只把“学习闯关”从静态清单提升为：

- 正式位置上的学习入口
- 有推荐下一步的抽屉
- 可点开的节点列表
- 有内容的详情区

这样既符合当前数据和接口边界，也能明显提升这块区域的可用性。
